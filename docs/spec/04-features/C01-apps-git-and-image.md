# C01 – Apps from Git and Docker image

## Summary

A user creates an `app` service from a Git repository or from a Docker image. Polipan builds (Git) or pulls (image), makes a Release, deploys it, and shows status. This is the core of the panel. Deploy behaviour is in [08-deploy-engine](../08-deploy-engine.md).

## User stories

- **US-APP-01** As a developer, I connect a GitHub/GitLab/Gitea repo and Polipan deploys it on every push.
- **US-APP-02** As a developer, I deploy a public or private Docker image by tag.
- **US-APP-03** As a developer, I pick a build method: Dockerfile or automatic (Railpack).
- **US-APP-04** As a developer, I set the port, start command, resources and replicas.
- **US-APP-05** As a developer, I restart, stop or start a service without a new build.
- **US-APP-06** As a developer, I run a one-off command or open a terminal in a container.

## Rules

- **REQ-APP-001** (MUST) A service has `source_type` `git` or `image`. For `git`: connection or public URL, repo, branch, build path (default `/`), builder (`dockerfile` or `railpack`), Dockerfile path (default `Dockerfile`). For `image`: image reference with tag or digest, optional registry credentials (a secret).
- **REQ-APP-002** (MUST) A Git build clones the commit, builds with BuildKit, pushes to the registry, and records the image digest in the new Release. The same commit and config MAY reuse a cached image (BuildKit cache), but always creates a new Release row.
- **REQ-APP-003** (MUST) For `image` sources, the tag is resolved to a digest when the Release is created. The Release stores the digest. A moving tag (`latest`) never changes a Release.
- **REQ-APP-004** (MUST) Git auto-deploy: a push to the tracked branch (webhook signature valid) queues a Deployment with `trigger = git_push`. It is on by default for non-protected environments and off for protected ones until an admin enables it ([10-security](../10-security.md#3-roles-and-permissions)).
- **REQ-APP-005** (MUST) Railpack mode detects language and runtime without a Dockerfile. Detection failure gives the error `build_failed` with the detector message.
- **REQ-APP-006** (MUST) Service config includes: `ports` (container ports), `command`, `entrypoint`, `workdir`, `resources` (`cpu_limit_millis`, `memory_limit_bytes`), `replicas` (default 1), `stop_grace_period`, `restart_policy` (default `always`), `pre_deploy`, `deploy` (strategy options), `health`, `placement`, `failover`. Exact schema: [07-config-as-code](../07-config-as-code.md).
- **REQ-APP-007** (MUST) Build logs stream live over SSE and are kept as `deployment_logs`. Secret values are masked.
- **REQ-APP-008** (MUST) A manual "Deploy" button and `POST /services/{id}/deploy` deploy the current config and the latest commit of the branch (or a given commit SHA).
- **REQ-APP-009** (MUST) Stop and start change `desired_state` of the service. A stopped service keeps its Release and volumes, and its domains return 503 with a Polipan page.
- **REQ-APP-010** (SHOULD) Exec: a WebSocket terminal (`/services/{id}/exec`) into a running container, permission `service:exec`, audited, 15 min idle timeout.
- **REQ-APP-011** (MUST) Private Git repos use a Git connection (GitHub App, GitLab/Gitea token) or a deploy key (SSH key pair generated by Polipan: the private key is stored as a secret, the public key is shown and kept in the service source).
- **REQ-APP-012** (MUST) A service name is unique per environment, lowercase `[a-z0-9-]`, 1–40 chars.
- **REQ-APP-013** (SHOULD) Build cache is kept per service. A user can clear it.

## States

Service-level state shown in the UI (derived): `no_release`, `deploying`, `running`, `degraded` (some replicas unhealthy), `stopped`, `failed` (last deployment failed and nothing live). Deployment states are in [08-deploy-engine](../08-deploy-engine.md#2-state-machine).

## Edge cases

- Push to a branch while a Deployment is active: the new one is queued and older queued ones are superseded.
- Two pushes in a row, the second commit's build is faster: Deployments finish in order of `created_at`. A later-created Deployment is never overwritten by an earlier one (the engine compares `created_at` before the switch).
- Repo deleted or token revoked: clone fails with `build_failed` and a clear message. The live Release is untouched.
- Image tag not found: Deployment fails at `building` (resolve step) with `image_pull_failed`.
- Dockerfile exposes no port and none is configured: the service is deployed as a `worker` style (no domain allowed). The UI asks for a port when the user adds a domain.
- Port 80/443/9443/51820 as a container port is allowed (container ports are private). Host port binding of reserved ports is refused.
- Replicas > number of eligible nodes: replicas are co-located, one warning shown.

## Acceptance criteria

- **AC-APP-01** Given a public repo with a Dockerfile, When the user creates an app and deploys, Then a Release with an image digest exists, the deployment reaches `live`, and the container runs that digest. (REQ-APP-001, REQ-APP-002)
- **AC-APP-02** Given an image source with tag `latest`, When the tag moves and the user deploys again, Then a new Release has a different digest and the old Release keeps its digest. (REQ-APP-003)
- **AC-APP-03** Given a valid push webhook on a non-protected environment, When it arrives, Then a Deployment with `trigger = git_push` is queued. Given an invalid signature, Then the response is 401 and nothing is queued. (REQ-APP-004)
- **AC-APP-04** Given a repo with no Dockerfile and builder `railpack`, When deployed, Then the image builds and runs. (REQ-APP-005)
- **AC-APP-05** Given a running service, When the user stops it, Then the container stops, the Release stays, and the domain shows the stopped page. (REQ-APP-009)
- **AC-APP-06** Given a build log containing a secret value of the service, When stored, Then the value is replaced with `***`. (REQ-APP-007)
- **AC-APP-07** Given a developer on a protected environment, When they try to exec into a container, Then the response is 403. (REQ-APP-010)

## Out of scope

Monorepo auto-detection of many services. Build on a separate remote builder node (later).
